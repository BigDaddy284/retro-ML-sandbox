# Changelog

All notable changes are recorded here, one entry per completed task. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- T-877: the go's log line names every reward that paid instead of three and "and N more".
- T-876: the Rewards panel's warning line uses the theme's warning colour.
- Changed: the app now has the look of Stills & Reels and StackSpace, with the same colours value for value: dark by default, a light mode and Match Windows (a toolbar button switches and the choice is remembered), the blue-to-purple accent on the Research button and the picked tab, rounded buttons, capital section headings, dark scroll bars and, on Windows, a title bar in the app's colours; each panel keeps a thin coloured strip so children can tell them apart (T-886).

- Added: a value search over all of the game's memory, like a cheat finder: start from every byte or a number (12, 0x0C, $0C), then keep the bytes that are exactly a number, went up, went down, changed or stayed the same since the last scan (T-884).
- Changed: the "What the AI is doing" panel no longer shows the "Watching N values…" line twice, its three lists have bold headings, and "Try the buttons", "Share what it learned…" and "Load shared knowledge…" sit on one row (T-883).

- Changed: the Research window shows its four sections as tabs (Learning settings, The situation now, Memory, Step log), so each table uses the whole window instead of three rows; each learning setting's explanation is written under it, and the Memory and Step log tabs show how many rows they hold (T-880).
- T-875: the chance of a random move now also falls with the steps learned (to its floor after 6,000 by default, about ten 40-second goes), not only by a little per go; the Research window's settings box has the number as "Exploring steps".
- T-874: the Rewards panel has a Controls group with a row for every button of the connected game and one for pressing the same button again, each at 0 until a person sets points; the summary counts only rows worth something.
- T-873: the Learning panel has "Each go lasts" and "Give up when nothing changes for" boxes in seconds; a person's choice is kept per game.
- T-872: a Points box in the Rewards panel takes any number for the picked reward (0.65, -3), applied on Enter or when leaving the box.

- T-869: a flag guess that switches more than once in ten steps is doubted at one review and dropped at the next, like a busy life count; the classifier no longer proposes a flag for such a byte.
- Fixed: the "changed while nobody pressed anything" doubt is no longer issued while the game is not listening (a title demo), where everything moves by itself and the real score was being dropped at every Start; after a long run on an older build, press "Start from scratch" in the Learning panel so the AI can find the real values again (T-868).
- Fixed: two flags switching back to their first value no longer count as the game starting over (the user's log: 88 goes in six minutes, each ended by a reset after 7 to 80 steps, blaming the same two flags); a restart needs a score, lives or progress number dropping back to its start, and goes cut short by the same values within 120 steps, three in a row, teach the AI those values cycle (T-867).
- Fixed: a "progress" guess whose byte changes more than once in ten steps, or goes down as often as up (the user's log: "Progress goes up" paying 117 times in one go once the lives guesses were gone), is doubted at one review and dropped at the next, like a lives guess; a real level, lap or checkpoint keeps its reward (T-866).
- Fixed: a "lives" guess whose byte changes more than once in ten steps (the user's next log: a life "lost" 496 times in one go, never regained) is doubted at one review and dropped at the next, and the AI no longer proposes lives for a byte that changes that often; a real life count, lost a few times a go, keeps its reward (T-865).
- Fixed: a "lives" guess that turns out to go up nearly as often as it goes down (the user's log: a life "lost" 116 times and "gained" 101 times in one go) is doubted at one review and dropped by the AI at the next, so it stops paying and costing points; a real life count, which is lost one at a time and restored on a restart, keeps its reward, and a guess a person confirmed is never touched (T-864).
- Fixed (tests): the BizHawk Lua host test checked the hand-back calls at a moment that depended on the host thread, so it failed now and then under load; it now waits for the whole hand-back (unpause, then the messages back) before checking the order; the Research window's memory test no longer depends on which bytes the AI happened to guess after two steps (T-863).
- Added: a Memory table in the Research window for grown-ups: every address whose byte behaves like game state (and every address the AI has a guess at), its value now, how often it changes, what the AI thinks it is and how sure, and the name a person gave it; a filter box (address, hex offset or name) and a "Name it" box that confirms the AI's guess under your name or makes a named value where it had none. Nothing is read from documentation: the AI learns, a person names (T-862).
- Added: "Add a reward" in the Rewards panel: pick a value the AI found ("Your position"), "goes up" or "goes down", and the points, and press Add; the row appears under Progression with its sentence, and "Remove" takes a row of your own out again (T-861).
- Added: a reward of your own on any value the AI knows going up or down ("Your position goes up: +2", "Your position goes down: -2"), earned every step the value moves that way; the AI's own suggestions leave such rows alone and they come back after a reconnect. This is the engine part (`RewardService.add_own` / `remove_own`, UP and DOWN events for asked-about values); the panel controls are T-861 (T-860).
- Added: picking a reward in the Rewards panel shows a plain sentence under the table saying what it means and what it is worth ("Losing a life: the AI loses 7.5 points each time."), with the AI's caveats, whether you set the value, and whether it is switched off; category headers explain their group on hover ("Survival: staying alive") (T-859).
- Changed: rewards, goal steps and the step-detection options are offered only for the AI's best guess of each role (one score, one lives, one health; up to three progress values and three switches) and named in plain words ("Your score jumps up", "Losing a life", "Progress goes up", "Progress (2nd guess) goes up"), never by address; a name you type in the Discovery panel is used as typed. The Rewards panel on Super Mario Bros. showed 88 rows, seven of them "Score at ram[…] jumps up" (T-858).
- Added: each "Go N ended by …" line in the log now says which rewards paid the points ("from Score at ram[0] jumps up +2,500.0 (120 times), … and 2 more"), and the go's record keeps the breakdown, so a log shows what the AI is really playing for (T-857).
- Changed: a score or progress guess that changes while nobody presses anything and ends up the same whatever is held (a timer, an enemy, the title demo) is doubted when the AI checks whether the game listens and dropped by the AI at the next check, so junk guesses stop earning points and setting goals; a confirmed guess is never touched and a dropped one stays in the Discovery panel for a person to put back (T-855).
- Fixed: the first column of the Rewards, Progress and Compare tables and the Research dialog's situation table (the names a person reads) is now wide by default and can be dragged wider; it was a stretch column Qt does not let a person drag, and it came out narrow (T-856).
- Fixed: when a call to BizHawk timed out, its answer arrived during the next call, which then saw the wrong request number and dropped the link; a late answer is now skipped and only the slow call is lost (T-854).
- Fixed: a step of many frames at normal speed (the five-second wait in the button search) made the BizHawk link give up after five seconds and drop, so the app disconnected shortly after Start; a step now waits long enough for its frames, and the `call_timeout_s` option really governs calls (it was the connect timeout before). The probe and the button search run the emulator at 64x when it allows and put the speed back afterwards (T-853).
- Changed: when the game ignores the AI and no button gets it going, the AI lets the game run for five seconds and looks again, three times in all, and then stops training and says so in the Learning panel instead of playing goes on a title demo and earning points from values that move on their own (T-852).
- Changed: when the AI searches for the button that gets the game going, a button whose press changed something lasting while the game still ignores the pad is pressed again, up to three times (on Super Mario Bros. the first Start during the demo only brings the title screen back; the next one starts the game), and the search waits five seconds after each press so a splash screen cannot hide the answer (T-851).
- Changed: the AI acts on its best 16 guesses of each kind (the values it watches for events, pairs up, rewards, sets goals on and learns the state from) instead of every guess in the knowledge; with 1,600 guesses on Super Mario Bros. that was most of the cost of every step and left the AI never seeing the same situation twice. The Discovery panel still shows every guess, and a confirmed one always counts (T-850).
- Changed: the long look (which notices counters that step at the same few places) no longer keeps pairing a value that steps nearly every frame, shows more than 16 faces, or stepped at too many places; with 1,600 believed values over a moving title demo that pairing was the largest cost of every training step (T-849).
- Changed: when training starts (and after a go that ended stuck or on a restart) the AI first checks whether its buttons change anything in the game; if not, it searches for the button that gets the game going right away instead of waiting for goes to prove the game is ignoring it (T-848).
- Fixed: a `dictionary changed size during iteration` error from the goal service while the AI played (the knowledge was read on one thread while the relationship finder rewrote it on another); the knowledge and the discovery service now take a lock (T-847).
- Fixed: a handful of values back at their start while hundreds of others are not no longer ends a go as "the game started over"; a restart now means at least half of everything that has moved goes home together (T-846).
- Fixed: values that go back to their starting value every few frames (an animation counter on Super Mario Bros.' title screen that the AI had taken for a score) ended every go at once as a "restart"; after three such goes in a row the AI notes that those values cycle, says so in the log and the evidence, and stops reading their return as the game starting over (T-845).
- Changed: the Discovery and Rewards panels redraw their lists a few times a second at most while the AI trains, instead of on every step, and the Discovery list is rebuilt only when a value was added or changed; a change you make yourself still shows at once (T-843).
- Added: when the game ignores the AI (a title-screen demo, a game-over screen) it works out for itself which button gets the game going, by pressing each one in turn and checking whether its own buttons matter afterwards; the answer is remembered with the game's knowledge and pressed whenever the game stops listening, and later goes start inside the game. Nothing is assumed per game: the old default of pressing Start when stuck is gone (T-844).
- Changed: the suggested rewards and objectives are rebuilt only when a relationship the suggestions read actually changes, not on every step the finder reports one, and merging a goal with many objectives no longer slows down with their number (T-842).
- Changed: with a lot of known values (1,600 on the user's Super Mario Bros.) the app did more work per step than the emulator; the detector and the long look now keep their list of watched values until the knowledge changes, and a value's confidence is worked out once instead of on every read (T-841).
- Added: the log file now says how each go ended (reset, step limit, stopped, disconnected), with its steps, frames and points, and for a reset which values the detector saw going back to their start (T-840).
- Fixed: the automatic button experiments no longer run in the middle of a go; each one took a save state and ran a trial per button over the AI's link, freezing play for seconds every ten seconds on the real emulator. A due experiment now runs between goes, and not at all while the child plays in manual mode (T-839).
- Fixed: a "reset" (everything back to the start) now needs one of the values going back to its first value to be at least fairly sure; on the real Super Mario Bros. two shaky stack bytes going home together ended every go after 3 steps (T-838).
- Added: the six panels are dock widgets that can be dragged to another edge, tabbed together, floated as their own windows, resized, hidden and shown again from the toolbar's Panels menu, with Reset layout; the arrangement is remembered between runs (T-837).

- Fixed: picture and sound memory (OAM, nametables, VRAM, palettes, CGRAM, APU RAM) is no longer watched; on the user's Super Mario Bros. it made 1646 watched values and 1442 suggested rewards, and its bouncing sprite bytes read as lives lost and as resets, ending every go after a step or two (T-835).

- Fixed: NesHawk's "CPU registers" pseudo-domain threw on every frame step after the handshake had probed it; register domains are no longer watched, and any region the emulator refuses mid-game is dropped from the next step instead of stopping the game. EmuHawk's "<picture> saved." message on every screenshot is silenced while connected (T-833).
- Fixed: on the user's EmuHawk one memory domain threw a .NET exception on every read, which stopped every frame step with an error that named nothing. The BizHawk script now leaves out, at connect, any domain it cannot read (and says which in the Lua console), and a read that fails later names the domain, address and length (T-832).

A step now unpauses, runs its frames and pauses again; the Lua test host runs EmuHawk's real loop order so this cannot pass unnoticed again (T-831).
- A profiling tool, `python -m retro_ai_lab.tools.profile_play`, plays for a few seconds in the real window against the simulator or a running emulator and prints what the emulator's round trips and the app's own per-frame work cost; the bridge link now also keeps per-command totals since connect (T-830).
- Fixed: closing the window while a frame step was still waiting on the emulator logged an uncaught "Signal source has been deleted" error from the worker thread (T-829).

- Fixed: with BizHawk, the app watched every memory domain every frame, ROMs and the whole system bus included (about 100 KB a frame on a NES, with reads that can poke hardware registers), which could make each frame step take seconds and the screen stay blank. Only live RAM is watched now (T-827).

- Adapters can step, read several memory regions and take a screenshot in one request (`step`, `read_many`), and memory snapshots use one request (T-822).
- Button presses go to the emulator on a worker thread, so pressing a button no longer stalls the window (T-821).
- Fixed: pressing Disconnect while the game was being stepped could be reported as a lost link (T-820).

- The play clock steps the game on a worker thread as well, and a link dropped by two workers at once is reported once (T-818).
