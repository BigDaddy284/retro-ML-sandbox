## 3. Emulator adapter contract

Every adapter subclasses `retro_ai_lab.emulator.EmulatorAdapter` (T-003). The public methods are `final` and perform the checks every backend must share; subclasses implement `_do_*` hooks only.

```python
class EmulatorAdapter(ABC):
    name: ClassVar[str]           # registry id, e.g. "bizhawk"
    display_name: ClassVar[str]   # child-facing name

    # lifecycle (idempotent)
    def connect(self, timeout_s: float = 5.0) -> None
    def disconnect(self) -> None
    is_connected: bool
    def mark_disconnected(self) -> None   # backend reports a dropped link

    # description (require connection)
    def capabilities(self) -> Capabilities
    def game_info(self) -> GameInfo
    def buttons(self) -> Sequence[Button]
    def memory_regions(self) -> Sequence[MemoryRegion]        # memory_read

    # operations (require connection + capability; arguments validated)
    def read_memory(self, region: str, offset: int, length: int) -> bytes   # memory_read
    def capture_frame(self) -> Frame                                        # screen_capture
    def set_input(self, pressed: Iterable[Button]) -> None                  # input
    def advance_frames(self, n: int = 1) -> None                            # frame_advance
    def read_many(self, reads: Sequence[tuple[str, int, int]]) -> tuple[bytes, ...]   # memory_read, one request
    def step(self, frames=1, *, pressed=None, reads=(), screenshot=False) -> StepResult  # T-822: one request
    def set_speed(self, multiplier: float) -> None                          # speed_control
    def save_state(self, slot: str) -> None / load_state(...)               # save_states
```

Rules enforced by the base class:
- Any operation while disconnected raises `EmulatorDisconnectedError`.
- Any operation whose capability flag is off raises `UnsupportedCapabilityError(capability)` before the backend is touched.
- Bad arguments (unknown region or button, out-of-range read, non-positive speed or frame count, unsafe slot name) raise `ConfigurationError`.
- A backend that returns the wrong number of bytes from a read is reported as an error rather than passed through.
- Hooks for optional capabilities have defaults that raise `UnsupportedCapabilityError`, so an adapter only implements what it supports.
- `step` and `read_many` (T-822) bundle what the UI needs each frame; their default hooks compose the primitives, and `BizHawkAdapter` sends one `step` / one `read` request instead. Each part of a `step` is checked only when used, so a step without a screenshot works on an emulator that cannot capture its screen.
- One conversation at a time (T-817): every public operation holds the adapter's re-entrant lock, because the Game panel captures frames on a worker thread while the GUI thread (play clock, training, watchdog) may be talking to the same socket. `check_link()` never waits for that lock: if another thread holds it, the link is evidently in use and the answer is True.

**No experiments over a busy link (T-839).** `DiscoveryService` runs its scheduled button experiment from inside the snapshot handler, so on the real emulator it froze the window and the game for seconds mid-go; `TrainingService` sets `experiments_allowed` off at start and on at stop, in every mode, and in an AI mode runs a due one between goes (`run_due_experiment`, before the next go restores the checkpoint); the panel's on-demand experiment is unaffected.

**Per-step cost with a lot of knowledge (T-841, T-842).** On the user's Super Mario Bros. the knowledge held 1,600 values and 2,400 suggested rewards, and the app did more work per step than the emulator: `Variable.confidence` was recomputed from the evidence on every read, the event detector and the long look rebuilt their believed lists from the whole knowledge on every snapshot, the reward and goal services rebuilt every suggestion whenever the finder reported a relationship (most steps), and `merge_suggestions` searched the goal per objective. Now `Variable.confidence` is a field set once in `__post_init__`; `Knowledge.version` counts variable changes and the watch lists are kept per `(version, snapshot regions)`; `RelationshipWatch` lets the services rebuild suggestions only when the set of confident relationships (id and level) changes; the merge indexes by trigger key and `Goal.observe` builds one completed set per event. Measured in the real window against the simulator with 1,610 values: 8 steps a second before, 43 after.

**Cycling values are not a restart (T-845).** A reset event names the values it blamed (`GameEvent.variables`); `EpisodeSignals` keeps them; `TrainingService` counts goes ended by a reset within three steps blaming the same group and after three in a row calls `DiscoveryService.doubt_reset`, which adds `cycles` evidence (weight 0) to each and announces the change; `EventDetector` leaves a value with that evidence out of the reset judgement. A restore puts values home at frame 0 of a go, which the runner already ignores, so a real restart cannot follow within twelve frames three times running.

**A restart is most of the game going home (T-846).** The detector counts the watched values that have ever left their first value and declares a reset only when the values going home together are at least `RESET_SHARE` (half) of them, on top of T-838 and T-845. On the user's Super Mario Bros. with 1,600 believed values some handful was home on nearly every step; a different handful each time, so T-845's three-in-a-row rule rarely fired.

**The knowledge is safe across threads (T-847).** Snapshots are published from the play clock's worker and from the training step on the GUI thread, and every handler runs on the publisher's thread, so the finder could rewrite relationships while the goal service walked them (the user's log: `dictionary changed size during iteration`). `Knowledge` keeps an `RLock` around every edit and every walk (iteration hands out a copy), and `DiscoveryService` drives its detector, finder and long look under one lock in `_on_memory`, `review`, `experiment` and `doubt_reset`.

**Panels follow training a few times a second (T-843).** `DiscoveryUpdated` and `RewardProfileChanged` arrive on most training steps; rebuilding 1,600 list rows or 2,400 tree rows each time was the largest per-step cost left on the user's PC. `ui/coalesce.py`'s `Coalescer` runs the first request at once and folds the ones that follow within 250 ms into one run when the window closes. The Discovery panel rebuilds its variable list only when a variable was added or changed (events alone refill the events, relationships and summary); the Rewards panel coalesces the AI's "suggestions" changes only, so a person's own control shows at once.

**The AI works out how to start the game (T-844).** Nothing about a game is coded in, so when the game ignores the AI (a title-screen demo, a game-over screen) it finds the way out by experiment. `understanding/wakeup.py`: `inputs_matter` saves the spot and plays the same frames holding nothing and holding each playing button in turn (ending with idle frames so a controller mirror settles), and says whether memory ends up different; `find_wake_button` presses each console button in turn (the remembered one first), waits for the game to settle (a splash screen), and accepts the first whose press changed something lasting *and* after which the playing buttons matter, leaving the game running there. `EpisodeRunner` keeps a fingerprint of each go (its first state keys) and whether the actions varied; when a screen stops changing it presses the wake button the service gave it, or ends the go `stuck` when none is known. `TrainingService` runs the search before the next go when a go was stuck from its first step or two goes ran identically although the buttons differed, remembers the answer in `Knowledge.wake_button` (saved with the knowledge, shown in the Discovery summary), hands it to the runner, and takes a new checkpoint inside the game so later goes start there. A go stuck part-way (the lives ran out) just gets the checkpoint back, as every go does. The old default of pressing Start when stuck is gone; the action space still keeps Start and Select out of play, which is about not pausing the game, not about any game's menu.

**Every go starts by asking whether the game listens (T-848).** The T-844 triggers wait for goes to prove the game is ignoring the AI, and on a title demo that keeps the screen moving the user's go ran 125 steps without proving anything. `TrainingService._listens` restores the checkpoint and runs `inputs_matter` with the AI's playing buttons at the first go after Start and after any go that ended stuck or by a reset; a game that does not listen goes straight to `_wake_up`. The probe costs about 120 frames of the link, so it does not run before every go, and it is skipped (as listening) without save states.

**The long look's pairing is bounded (T-849).** `LongLook.observe` recorded, for every believed flag/progress/position value that stepped up, where every believed position/progress value was: quadratic in the believed values, and on the user's title demo (hundreds stepping every frame) 35 ms a snapshot with 3,400 values. A stepper is dropped from pairing once it has shown more than `FEW_VALUES` faces or, after `SETTLED` observations, stepped up on more than one in `TOO_FAST`; a (stepper, driver) pair is dropped once it holds more than `MAX_PLACE_VALUES` driver values, since those can no longer form `FEW_PLACES` places. `LongLook.tracking` lists what is still paired.

**The AI acts on its best few guesses of each kind (T-850).** `Knowledge.believed(at_least, regions=None, per_kind=BELIEVED_PER_KIND)` returns at most 16 non-rejected variables of each kind at or above `at_least`, seated by confirmed first, then confidence, evidence weight and address, in the knowledge's own order; with `regions` only memory the emulator shares competes. The event detector, the long look, `StateEncoder`, the reward suggestions, the goal suggestions and the goal panel's trigger options read it; the Discovery panel, `needs_help` and the knowledge file still hold everything. On the user's Super Mario Bros. 1,600 guesses had meant 1,000 events in seven snapshots, 41,000 relationships, 5,000 reward behaviours and a state the agent never saw twice; the churn profile went from 6 steps in 13 s to 100 steps a second.

**A promising button is pressed again (T-851).** The first search on the user's Super Mario Bros. tried every button once and gave up: Start during the title demo brings the title screen back (a lasting change) but the pad is still ignored until the *next* Start, and the "WORLD 1-1" splash that follows ignores it for a few seconds more. `find_wake_button` now gives a candidate up to `DEFAULT_PRESSES` (3) presses: after a press that changed something lasting but left the playing buttons not mattering, it saves that spot (`PRESS_SLOT`), plays the wait once more from it as the new comparison, and presses the same button again from there; a press that changes nothing lasting moves on to the next candidate, so a button that merely toggles a menu option is pressed at most three times. `DEFAULT_WAIT` is 300 frames. Nothing is assumed about which button or how many presses; the log says how many it took.

**No go runs while the game ignores the AI (T-852).** After the failed search in the user's log, a 600-step go on the title demo earned 9,557 points from values that move on their own, which teaches the brain and the knowledge nothing true. `TrainingService._wake_up_or_wait` gives a deaf game `DEAF_TRIES` (3) searches, letting it run `DEAF_WAIT` (300) frames between them with a fresh checkpoint each time (an intro may still be playing), and when all fail it ends training (status IDLE, `TrainingStateChanged` reason "not listening") and logs `NOT_LISTENING`, which the Learning panel shows as its note: get the game going yourself, or pin a spot inside it, then press Start again. An emulator without save states cannot run the search and keeps the old behaviour.

**A long step waits for its frames, and the search runs flat out (T-853).** The user's 23:04 log showed the search's first 308-frame step at normal speed taking 5.1 s, the link's 5-second timeout firing, and the stale answer desynchronising the next call so the link dropped. `BizHawkAdapter._do_step` and `_do_advance_frames` pass `call_timeout_s + frames / SLOWEST_FPS` (30) as the wait for that call; other calls keep `call_timeout_s`, which `open_link(call_timeout_s=...)` now hands to the link (before, calls used the connect timeout). `BizHawkSimulator(frame_delay_s=...)` makes frames slow for tests. `TrainingService._flat_out()` runs the emulator at `FAST_SPEED` around the listening probe and the wake-button search when it has speed control and is not already fast, and restores 1x afterwards, so nobody watches a demo for a minute.

**A late answer is skipped (T-854).** A call that times out leaves its answer in the socket; before, the next call read it, saw the wrong id and closed the link with a protocol error, which is how one slow step became a disconnect. `Link.call` now reads until its deadline and skips well-formed answers to earlier ids (`_late_answer`, logged), while an answer to a later or unknown id, or anything malformed, still closes the link.

**Guesses that move by themselves are doubted, then dropped (T-855).** The user's first goes inside Super Mario Bros. earned 15,000 to 24,000 points each from about 1,600 score and progress guesses born while the title demo played. `understanding/wakeup.py`'s `probe_inputs` (which `inputs_matter` wraps) returns an `InputProbe`: whether the buttons matter, and the `self_moving` bytes, those that changed during the idle run, are not noise (the two idle runs agree on them) and are not input-driven (the busy run ends with the same value). `TrainingService._listens` hands that set to `DiscoveryService.doubt_self_moving`, which adds `moves-alone` evidence (weight 0) to each unconfirmed SCORE or PROGRESS guess covering such a byte and rejects it (`by="the AI"`) when it already carries that evidence. A racer's score that climbs while coasting answers to the brake, so it is input-driven and safe; lives and health are left out because standing still is a fine way to lose them (the Toy Racer's own Lives was the first casualty of a wider rule). Position, speed, flags and counters are allowed to move. Known limit: progress that advances on its own and ignores the pad (an auto-scroller) would be doubted; a person can confirm it. A rejected guess leaves `Knowledge.believed` and so the rewards, goals, state and detector at once, stays in the panel as a record (so it is not re-proposed), and a person can still confirm it.

**A restart with a life lost waits for its search (T-1013).** In `EpisodeRunner.step()` the order was: `_settle` (count, pay, learn, and end the go on a restart), then, if a life went, `_seek`. Toy Hopper, like many games, puts the player back at the start of the level when a life goes; once the engine has learned the values that return to their start there (flags and progress; on level 0 from about the eighth go on, and mostly for a death further in than the first gap) it publishes a RESET in the same update as the SETBACK. `_settle` then set `_ended_by = "reset"` and returned False, and `step()` returned before `_seek`: found by writing down every `_settle` and `_seek` of 14 goes, where each go that ended "reset" did so in the step of its second loss with two searches left. Now `_settle` does not end the go on a restart when a life was lost in that step, the step is the AI's own (`source == "ai"`), it is not the go's last step, and `_way_back()` is not None; it sets `_held_reset` instead. `_way_back()` is the test `_seek` already made, moved into one helper so the two cannot disagree: moments kept with one at least the lead back and carrying a `Mark`, `_ways_left`, a screen watch, and a life value known; it returns the moment, the moves since and the life values. The step itself is settled exactly as before (learned with `done=True`, the penalties paid). `step()` then runs `_seek`; if the count of goings back did not move, no way was found, and the go ends "reset" there with the game put back to after the loss, the reset's detail still in `last_reset` for the go's line; if it moved, the go carries on, and the runner says so in the log once (then at DEBUG). `go_back` already tells the observation to expect the jump and drops what the signals collected, so no second restart is seen. Not held: a restart with no life lost, a step somebody else drove (`observe_step` forgets the moments anyway), a go with no search left or a runner that has given up. A restart the engine reports a step after the loss needs nothing: the search ran at the loss, and after a way found the game is no longer where the restart would be seen. Measured, 40 goes: level 0, 3 goes end "reset" (19), a way in 101 of 110 searches, 1,020 then 936, 950 over all 40 (833 then 996, 745), 227 s (158: more searching); level 3, 861 then 1,413, 1,074 over all (826 then 704, 712), best 2,020 of 2,496, a way in 88 of 95. 37 and 33 of the 40 goes now end at the bench's 300 steps, which at 8 pixels a step is 2,400 pixels at the very most: the bench's limit is the next thing in the way of seeing a level finished, with the walls of level 3 (452 and 996).

**The plain way first (T-1012).** `find_way(..., plain=None)` in `training/search.py`; `PLAIN_SHARE = 0.5`. What was measured before anything was built: every search of T-1011's two 40-go runs was written down with the moves it was given. 54 of 179 found no way, and they were not, as T-1011 supposed, mostly two-button moves (seven were): they were wanders, such as eleven steps left and then a jump twelve steps long that comes down short of the gap. 33 of the 54 ran out of changes before they ran out of tries. On those 54, exchanging one button for another found a way in 14, some after 140 to 300 tries; holding "right" from the same save, cut at the step that loses the life, with the ordinary `ways.changes` on it, found a way in 48, on try 14 to 52. On all 179 the plain way finds a way in 154 and what it did in 125, together 173; the 19 that only what it did solves are a plain walk stopped by a wall the go had jumped (alive, no new ground) or killed by something earlier the go had got past. So with `plain` (a move) the search has two parts. First the plain way: `(plain,) * (len(trace) + carry_on)` played blind; if it stays alive it is played once more under a trial watch and is the way if that counts new ground (`Way.change` is then that move held from step 0, `lost_at` None); if it loses a life at step k, `changes((plain,) * k, space)` are tried while the tries are under `int(budget * PLAIN_SHARE)`, and a way found carries `plain` and `lost_at=k`. Then, as before, the changes to `trace` up to `budget`. One inner function (`seek`) plays both lists, and a set of the move lists already settled (lost blind, or looked at) is shared between them, so where what it did was the plain way the second part goes on down the list at no cost instead of starting again; a change that stayed alive blind when the first part's tries ran out is not in the set, because it was never looked at. The moves of `trace` and `plain` are checked against the controls before anything is played. `budget` and `seconds` hold over the whole search, so `test_search.py` passes untouched and a search with `plain=None` is the search of T-1006. The runner (`_seek`) passes the first of `_paid_moves()`, the buttons paid so far, best first, each with its own one-button move (the list pressing on picks from, T-1011, now one helper); with nothing paid, none. Its log line for a plain way reads "holding right instead of what it did, with right + a for 4 steps, starting 17 steps before that would lose the life." Where the go did walk plainly the same change is found one play later than before (19 instead of 18 at the first gap: the plain way's own play), which is why three pinned counts in `test_search_at_a_loss.py` moved by one and its pinned sentence changed. Measured, 40 goes: level 0, a way in 75 of 78 searches (65 of 88), 3,350 tries in all (5,349), 833 then 996, 745 over all 40 (703 then 574, 605), 158 s (202); level 3, 67 of 75 (60 of 91), 3,618 tries (6,528), 826 then 704, 712 over all (599 then 512, 588), no go short of the first gap (7), 191 s (285). Seen in these runs and left for its own task, next: on level 0, 19 of the 40 goes end "reset" at the walker with two of their three searches unused, because that death arrives in the same step as the restart it reads as, and a go that ends is not searched.

**Pressing on (T-1011).** `EpisodeRunner(..., press_after=0, press_for=PRESS_FOR)` (16); the training service passes `press_after=PRESS_AFTER` (24) to a runner that goes back and 0 to one that does not. Why it is needed: recorded choice by choice, the network's values a few steps short of a gap are about the same for every move, and the moves that leave the game as it is ("nothing", "b") come out on top, because a step of waiting is worth the discount (0.99) times the place's worth while going on has cost lives there. Nothing changes, so the same choice is made again until the go ends "stuck"; no life is lost, so nothing is searched. What the runner does about it is not in the learner: `_settle` counts the steps since anything was paid (`_unpaid`) and adds each paid step's pay to every button of its move (`_paid`, kept over the runner's goes); `_press_on`, called in `step()` when no list of moves is being played, queues the one-button move of the best-paid button `press_for` times once `_unpaid` reaches `press_after`, but only where a search could follow (`moments` kept and `_ways_left > 0`, so never once the runner `gave_up`). The steps are ordinary steps: learned from, counted, looked at. A press that ran its course unpaid moves `_press_next` on to the next-best-paid button (round and round); any pay sets it back to the best, and a press cut short by a life lost is not one that got nothing. A button with no move of its own is passed over. A go about to end "stuck" presses on first whatever `_unpaid` says (the last pay can come a step or two after the last change, and the go used to end one step before the press was due), once for each standstill (`_pressed_stuck`, cleared when the state changes); if the press changes nothing the go is stuck as before, and a wake button is pressed as before. The press's own steps count as unpaid, so with 24 and 16 a brain that goes on getting nowhere has 8 steps of its own between presses. `EpisodeResult.pressed_on` is saved (an older record reads 0) and the go's line ends ", pressed on N times". Tried first and set aside: never repeating a move that changed nothing (the brain dithers instead of standing: level 3, 258 then 306), and 60 goes of practice from a spot 88 pixels before the first gap (the share of goes that cross falls from 8 in 10 to between 0 and 4 in 10 although 51 ways were found there: this brain does not learn the jump from more practice at it, which must start within about 10 pixels of the edge and be held for six steps). Measured, 40 goes: level 3, 599 then 512, 588 over all 40 (T-1010: 417 then 212, 392), 7 goes short of the first gap (21); level 0, 703 then 574, 605 over all (410 then 440, 463). Lives lost a go: 0.9 and 0.9 on level 3, 0.6 then 1.6 on level 0. Seen on the way and left for their own tasks: a search finds no jump when the moves before the death were two-button moves ("b + right" plus one more button is no move, so "hold one button more" cannot make it jump); the walker on level 0, where a way found leaves the player inside the walker's beat; pay stops for five steps where the measure of progress changes from where the player stands to the camera's travel; on a screen where the camera already follows the player when the AI first looks for itself, it takes a piece of scenery for itself (found by pinning a spot mid-level before the eyes had been set up).

**Going back, switched on (T-1010).** `TrainingService(..., ways_per_go=WAYS_PER_GO, way_seconds=WAY_SECONDS)` (3 and 15.0; 0 switches it off). `_on_connected` keeps whether the console has save states; `_ensure_runner` then gives the runner `Moments(BACK_SLOTS)` (`back0` to `back5`, apart from the watch's `player` slot and the runner's own `back_now`), `ways_per_go`, `way_seconds`, `give_up_after=GIVE_UP_AFTER` (8) and `flat_out=self._flat_out`, the service's own way of raising the emulator's speed (a no-op while training already runs fast). Without save states the runner gets no moments and 0 ways, and is what it was. Because the runner is rebuilt for a new connection or a new brain, having given up lasts no longer than that. A search runs inside `TrainingService.step()` on the worker thread with the service's lock held, so Stop and Pause wait for a search in flight: 15 seconds at most. The practice bench passes `way_seconds=None`, since a limit in seconds would make its counts depend on the machine, and stops scoring the camera's move across a going back (the look before and the look after are not neighbours). What it measured, 40 goes, furthest reached in the first ten then the last ten: level 0, 410 then 440 with a best of 912 (T-998: 242 then 194, best 449); level 3, 417 then 212 with a best of 1,197 (222 then 151, best 244); a way found in 40 of 64 and 32 of 56 searches. Two of the bench's own measures fall on level 0 with it on, and are for later tasks, not hidden: the camera's move is measured right in 73% of looks (98% before) and the ground count matches the game's camera in 38% of goes (98%), because the goes now reach x 300 to 450 where the camera's move is read as 12 pixels for 16; and the deaths explained fall to 71% because more of them are walkers further in, which the eyes do not yet blame. Late in training on level 3 the brain turns timid (last ten 212, many goes ended by standing still). On the racing practice game going back seldom finds a way and gives up (52 searches over six trainings of 30 goes); the one or two ways a training does find come early and steer the rest, which is why `test_first_working_demonstration` sums six learner seeds now: its claims held for 20 of 20 threes of the six seeds without the search and 17 of 20 with it (all three failures with seed 3), and over all six together with room (score a step 2.75 against 1.86, speed 3.15 against 2.46, crashes a step down to 0.49).

**Giving up on going back (T-1009).** `EpisodeRunner(..., give_up_after=None)`. A way past is told by new ground, and in a game where the eyes count none (the racing practice game: a way in 4% of searches, against 77% on the platform game) every search is its whole budget of plays for nothing. Nothing known before a search tells such a game apart (the ground counted in the go when the life went overlaps between the two), so the runner goes by what its searches come to: `_missed` counts those that found no way (out of time included; one ended by an emulator error is not counted), in a row and across goes, and a way found sets it to 0. At `give_up_after` the runner has `gave_up`: `begin()` gives a go no searches, so `_keep_moment` saves nothing and `_seek` only forgets, and its goes are what they were before T-1007. It says so once: "Going back found no way past 8 times in a row, so the AI stops going back in this game: here it only costs time." It lasts as long as the runner does; a new runner (a new connection, a brain forgotten or moved to a network) starts counting afresh. Also corrected here: T-1007's note that ground walked again after going back is paid again was wrong. `Ground.put_back` keeps what was reached, so a way played over ground the go had covered pays nothing until it is past the furthest the go had been (checked on the practice game: the 23 steps back to the gap pay 0).

**A search's time (T-1008).** `find_way(..., seconds=None, clock=time.monotonic)`: with `seconds`, the same check that guards the budget before every play (the looked-at second play of a change included) also refuses to start one once that long has passed since the search began; a play in flight is finished (at most the trace and `carry_on` steps). `Search.seconds` is how long it took (always measured, and left out of equality: two searches that find the same in the same tries are the same search) and `Search.out_of_time` says the time, not the tries or the list, ended it. `EpisodeRunner(..., way_seconds=None)` passes the limit on; a search out of time is a loss that stands like any other. The log line carries the time: "... found a way past on try 18, after 0.3 s: ...", "... made 120 tries in 2.1 s: none got past.", and for a search out of time "... made 57 tries in 15.0 s, all the time a search may take: none got past." With a limit a search is no longer the same on every machine, so nothing that must be repeatable (the tests, the practice bench) should set one it can reach.

**Searching at a life lost (T-1007).** `EpisodeRunner(..., ways_per_go=0, way_tries=BUDGET, flat_out=None)`. With `moments`, a screen watch and `ways_per_go` of 1 or more, `step()` ends with `_seek()` when the step of the AI's own lost a life and the go did not end. The loss is settled first like any other (counted, penalised, told to the death watch), so it stays real to the learner. Then, inside `flat_out()` if one was given: the present is saved into `NOW_SLOT` (`back_now`, a name `Moments` may not use), and `find_way` runs from `moments.before_loss()` with the variables the go counts lives on and `watch.trial(mark)`. A way found is handed to `go_back(moment, then=way.moves)` and played through the ordinary step, so it is looked at, paid and learned from; with none the save of the present is loaded (the observation never saw the tries, so there is no jump to announce) and the go carries on a life down. A loss that stands forgets the moments: every try from before it would lose that life again first. The same when no search is possible (no watch, no moment far enough back, no mark, no life variable, none of the go's searches left). A go that has used its searches makes no more saves. A life lost while a way is being played drops the rest of its moves. An emulator error in a search ends the go "disconnected". `EpisodeResult.ways_sought` / `ways_found` (0 when read from an older record) and `describe_ways()` report it, and the log has one line a search: "Lost a life at step 36. Went back 36 steps and found a way past on try 18: right + a for 4 steps, starting 17 steps before the life went." With `ways_per_go=0`, the default, nothing is searched and the moments are left alone, as in T-1005. Known: a loss that ends the go (the last life) is not searched.

**The search (T-1006).** `training/search.py`'s `find_way(connection, slot, trace, space, frames_per_step=, lives=, watch=, budget=BUDGET, carry_on=CARRY_ON)` takes `ways.changes(trace, space)` in order, applies each with `carry_on` = 20 steps more on the end and plays it from the save with `trial.play`: blind first (no screenshot; a life value going down ends it), and a change that stays alive once more with `watch()` (a fresh `ScreenWatch.trial(mark)` each time), which makes it the way only if that try is alive too and counted new ground (`Outcome.past`: alive is not enough). Every play counts against `budget` = 120, checked before each, so a search never overspends and always ends. It returns `Search(way, tries)` with `Way(moves, change, tries, ground)` or `None`, talks to nothing but the connection, and leaves the game where the last try ended: putting it back and any emulator error are the caller's. On the practice game, for a go that walked into the first gap, the way is "right + A for 4 steps, 17 steps before the life went" after 18 plays on level 0, and the same held 8 steps after 50 plays on level 3.

**A go that can go back (T-1005).** `EpisodeRunner(moments=)` takes a `Moments` (T-1003). In `step()`, before the move is chosen, `_keep_moment()` saves the game into `moments.next_slot()` when a save is due and records it with `ScreenWatch.mark()`; it saves only while `EpisodeSignals.watched` names a life or health value (with none, nothing can be seen to be lost), stops for good with one log line on a console without save states, and ends the go as "disconnected" if the link drops there. After the emulator step `moments.did(action)` records the move; the runner's own unstick press (`None`) and a step somebody else drove (`observe_step`) forget the moments and any moves still queued. `begin()` forgets them too: a new go is a new story. `go_back(moment, then=())` loads the moment's save, calls `expect_jump(back=True)` (T-1004) and observes, drops what the signals collected across the jump, flushes the steps waiting for their lookahead as final at the state before the jump, re-encodes the state, tells the watch of a life no look came for and puts it `back_to` the moment's mark, calls `moments.went_back`, and queues `then`: `step()` takes its move from that queue before it asks the learner, and the step is otherwise an ordinary one (looked at, paid, learned from, reported to `on_learned`). `steps`, `reward`, the lives lost and the fingerprint of the go are what was really played and do not go back; `times_back` counts the goings back. Refused with a `ConfigurationError` and nothing changed: no go running, a go that is over, no moments, a moment not kept, a move the controls don't have. An emulator error from the load is the caller's.

**A jump back is nobody's event (T-1004).** T-935 taught only the byte statistics that a restore is not a change. The event detector still judged the snapshot after a `load_state` like any other, so a restore reads as events: at the start of a go that is old behaviour the runner works around (it listens only after its first observation) and the restart it shows feeds T-904. For going back in the middle of a go, right after a death, `ObservationService.expect_jump(back=True)` marks the next `MemoryObserved` as `went_back` (that one only; a plain `expect_jump()` marks none and takes a pending mark off). On a marked snapshot `DiscoveryService._observe_memory` raises no event: `EventDetector.rebase` and `LongLook.rebase` take the values as they now are without judging or counting the move (first values, usual gains and all counts are kept), `RelationshipFinder.forget_recent` pairs nothing across the jump, the aftermath watch begins again as at a go's start, and the review and experiment counters do not move. Rewards and goals hear nothing because they only hear events. The rewards' own memory of a go's best values is left alone on purpose: ground walked a second time is not paid twice.

**Saved moments (T-1003).** `training/moments.py` is the memory the search at a death goes back with, and touches no emulator: the caller makes and loads the saves and tells it what happened. `Moments(slots, every=EVERY, lead=LEAD)`: `due()` (at once in a fresh story, then `every` = 20 steps after the newest moment), `next_slot()` (a free slot in the order given, else the oldest moment's), `saved(mark)` records the save just made there and returns its `Moment(slot, step, mark)` (the mark is the caller's: the screen watch's `Mark` of T-1000), `did(move)` one step played, `before_loss()` the newest moment at least `lead` = 30 steps back with the moves made since it (or `None`), `went_back(moment)` when the game was put back there (newer moments and the moves since are dropped, `steps` is the moment's again), `forget()` for a loss that stands. Moves are kept only from the oldest moment kept. `did(None)` is a step that is not the AI's own move (the runner's unstick press): the list of moves would have a hole, so everything is forgotten and a save is due at once. A moment is known by being the same object, not by looking the same: after a going back, a later save can have the same slot and step as one that was dropped.

**A start you can see (T-1002).** The first start of a freshly unzipped build can spend most of a minute before any of the app's code runs (the user's log: 20 s importing Qt, 20 s importing the app, 10 s creating the `QApplication`; the next start did the first two in a quarter of a second), so the built app carries PyInstaller's splash screen: `packaging/retro_ai_lab.spec` makes a `Splash` from `packaging/splash.png` (drawn by `packaging/make_splash.py`, kept in the repository), hands it to `EXE` and its Tcl/Tk files to `COLLECT`. **A try, off the record (T-1001).** `training/trial.py`'s `play(connection, slot, moves, space, frames_per_step=, lives=, watch=None, look_every=)` loads the save, plays one bundled `step` a move reading only the bytes of the `lives` variables, and stops at the first step in which one of them is lower than the step before. It goes through `ConnectionService.call` and nothing else: no `ObservationService.advance`, so no snapshot, no event on the bus, no reward, nothing for the change tracker or the learner (`test_a_try_is_off_the_record`). With a `ScreenWatch.trial` it screenshots on the steps a go would (`steps % look_every == 0`) and the watch's `take_new_ground()` is the outcome's ground. `Outcome(steps, lost, ground)`; `Outcome.past` is not lost and `ground >= PAST` (2). The pad is let go in a `finally`; the game stays where the try ended. A look costs about 15 ms of the app's time and a step without one almost nothing, so a search is meant to play a change without a watch first and look only at the ones that stay alive. Known gap: with no life or health value known every try looks alive, so nothing may be searched then.

**The watch goes back with the game (T-1000).** `Ground.keep()` returns a `Kept` (the camera's travel, where on the screen the player was first seen, where it stood from there), `Ground.put_back(kept)` makes that the place again and leaves the reach and the steps counted alone, and `Ground.copy()` is a separate count in the same state. `ScreenWatch.mark()` returns a `Mark` (the ground's `Kept` and where the player was last seen). `ScreenWatch.back_to(mark)` is for a save loaded mid-go: the tracker is reset so the jump is neither measured as a move of the camera nor taken for a cut, what was waiting from the last looks is dropped (a jolt, a life lost, which together would be read as a respawn and call `Ground.back()`; a fall; touches not yet blamed, let go), and the ground is put back; the counts for the ten-go summary stay. `ScreenWatch.trial(mark)` is a new watch on the same player with a copy of the ground put back to the mark and the same record of whether the camera can be followed: its `take_new_ground()` is what a try from that moment would be paid, measured against the go's own furthest, and its looks change nothing in the watch it came from. The kind the player was learned as is not handed over (a kind is a name in one tracker's catalogue).

**Ways past a death, the list (T-999).** `training/ways.py` has no emulator in it. `Change(at, move, hold)` is "from step `at` of what it did, make `move` for `hold` steps"; `Change.apply(trace, carry_on)` gives the moves to play, the trace with that stretch replaced (cut at the trace's end) and `carry_on` more steps of `carry(trace)`, the move it mostly made, so a try runs on past where the life went. `changes(trace, space, holds=HOLDS, stride=STRIDE, most=None)` yields them most promising first: holds of 4, 8 then 16 steps; within a hold from the end of the trace back every 2 steps; at each place the moves of `ActionSpace.near` for the move made there; a change that comes to moves already given is skipped. Why this shape: a scratch prototype on the practice bench went back to a save from at least 30 steps before each death and replayed the trace with such changes, learning nothing from the tries, until one got past alive, then played that one through for real. All 60 ways it found in two 40-go runs were a near move held 4 to 16 steps, 15 to 33 steps before the life went (the fall and the dying pause take the last 15), found in 9 to 142 tries. Simply putting the game back for more tries of its own, with or without more exploring and going over a lucky crossing again, did not help: it learned sooner to stay away. What plays a change and tells whether it got past, the saves during a go and the going back are the next tasks.

**What it tries is near what it would do (T-998).** `ActionSpace.near(index)` is the moves that differ from a move by one button and still hold a button it holds: one more button, or one of two let go (cached per move). Letting go of everything, and pressing one button from nothing, do not count, so an action space of single buttons has no near moves. `ActionSpace.sample_near(rng, index)` returns one of them `NEAR_SHARE` (half) of the time, each as likely as the next, and otherwise `sample(rng)`; with no near move it is `sample(rng)` with the same single draw. `QLearningAgent.choose` and `DQNLearner.choose` hand `Runs.next` a sampler around the move they would make at that step (`table.best(state)`, `_best(values)`; neither uses the random stream), so the run a try is held for (T-983) and how often a run starts are untouched, and learners on single-button controls, or whose own move is to hold nothing, draw exactly what they drew before. Why: getting over a gap is the run-up plus one button, held, and one pick in fifteen keeps the run-up. Measured from a saved spot 6 and 12 walking steps before the practice game's first gap, 400 tries, exploring 25% and 50% of steps around "hold right": any move 2 to 3% across on level 0 and 0.5 to 1% on level 3; half near 8 to 13% and 3 to 6%. The first rule tried also counted letting go of the last button as near; it crossed no more often and `test_runs_find_a_move_that_only_pays_when_held` caught it making things worse where buttons are not combined (the only move near "walk" was "stand still": 16 of 30 further seeds cleared the corridor against 23 before), so it was narrowed and that test is unchanged. The practice bench's figure for new ground changed with it: up to the look at which the game's camera first moves after the AI starts, the game's own figure is how far the player itself went (all the watch can count, T-993), and the camera's travel after; `Report.ground_before` counts the goes that began before it moved. The new picks keep the table learner near the start for two goes, which the old figure (the camera alone) marked wrong although the watch had counted the player's 39 and 49 pixels as 39 and 48.

**What rises at a loss (T-997).** `understanding/aftermath.py` holds `Aftermath`, fed by `DiscoveryService._observe_memory` with each observation's events and frame (`note(events, frame)`). A loss is a `SETBACK` or `RESET` event; losses within `AFTER` (30) frames of each other are one. A rise is a `PROGRESS` event. A rise is "met" when a loss comes up to `BEFORE` (90) frames after it or up to `AFTER` before it; a loss is "answered" for a value when at least one of that value's rises met it. Per value it keeps rises, met, answered, the losses counted before it first rose and the frames watched before it first rose. `verdict(var_id)`: rises and losses since it first rose are each at least `MIN_COUNT` (5), `losses * (BEFORE + AFTER)` is at most `QUIET` (a third) of the frames watched since, and both `met / rises` and `answered / losses` are at least `SHARE` (0.6). `begin()` (from `DiscoveryService.begin_go`, and by itself when frames run backwards) forgets pending rises and the last loss and banks the frames the go spanned. A new `Aftermath` is made with each knowledge (`_adopt`). `doubt_bouncing` asks it for every unrejected progress guess whose byte statistics raised no doubt, and treats a verdict as a third reason, `AT_LOSS` ("at-loss"), in the same flow as "busy" and "bounces": evidence the first time, rejection by the AI the second, a `Question` for a confirmed guess. Not judged: scores and flags; a rise more than `BEFORE` ahead of its loss; a loss with no memory event.

**The top of a clock (T-996).** `understanding/variables.clock_top(low, high)`: `_is_pair(low, high)` (the classifier's own 16-bit rule: the lower byte has rolled over, at least 60% of the upper byte's changes fell in a step in which it did, and the rest are no more than the upper byte's resets), `high.changes >= CLOCK_CHANGES` (3), and `low.same_hops >= 0.95 * (low.changes - 1)`. The change rate is deliberately not asked (`_is_steady` asks 90%, and a level clock that stops during a dying pause changes in 87% of steps). `DiscoveryService.doubt_self_moving(locations)` builds `_clock_tops(moved)`: for each byte the idle probe saw move, the byte above it when `clock_top` holds on the tracker's statistics. A guess of a kind in `CLOCK_KINDS` (score, progress, flag) starting on such a byte gets `CLOCK_TOP` ("clock-top") evidence the first time and is rejected by the AI the second, exactly as `MOVES_ALONE` works for a guess on the moving byte itself; the two are logged on separate lines and announced together. Both conditions are needed: one pace alone would condemn the page of a player who walks at one speed in a game without inertia (the probe holds nothing, and that position stands still), and moving alone would condemn a lap counter over a coasting car's position (which moves at varying pace). A clock that counts down is not covered: the tracker counts a roll-over only upward.

**A start that says where it stopped (T-995).** `cli._default_launch` logs each stage before it begins and imports in that order (`PySide6.QtWidgets`, then `retro_ai_lab.ui.app`); `run_app` logs "Creating the Qt application" and "Building the main window" the same way. `core/logbook.watch_start()` opens `logs/start-<pid>.txt` and gives it to `faulthandler` (`enable(all_threads=True)` and `dump_traceback_later(STUCK_AFTER)`, 10 seconds): the dump is written by a C thread that needs no Python to be running, so a hang with the interpreter lock held (a library loading, Qt's own start) is still written down. `started()`, called once the window is shown, cancels the timed dump; crashes stay watched for the whole run. `_end_watch` (at exit) closes the file and removes it when empty. `_carry_over`, at the next `watch_start`, logs every other run's non-empty trace under one warning each and removes the files (a file still open in a live run cannot be removed on Windows and is left). `log_failure(error)` writes an exception that is ending the launch and marks it (`LOGGED_MARK`), and the uncaught-exception hook skips a marked one: the windowed PyInstaller build never calls `sys.excepthook` for an exception that ends the script. `packaging/smoke_test.py` runs the built app with its data folder in a temp directory and fails unless the log names every stage in order and no trace is left. `faulthandler` is process-wide and pytest uses it, so the tests of the watch each run a child Python.

**A switch pays once a go (T-994).** `RewardService._score` has two gates before a row is matched: `PAST_BEST_KINDS` (progress and score pay only past the go's best, T-878) and `ONCE_A_GO_KINDS` (`FLAG_ON`, `FLAG_OFF`): `_first_time` keeps the `(kind, variable_id)` pairs seen this go in `_happened`, cleared on `GoStarted` and on connecting, and a pair seen before is dropped before it is tallied or published. The gate is on the event's kind, so it holds whatever points the row has, and a person's own rows (`UP`, `DOWN`) are not touched by it. `rewards/suggestions.py` adds `ONCE_NOTE` to the notes of the rows it builds for those two kinds.

**New ground, and the reward for it (T-993).** `observation/ground.py` holds `Ground`, the new ground of one go: the place is the camera's moves summed (`ObjectTracker.scroll`, T-992) once the screen has ever been seen to scroll (`scrolls`, kept from go to go), and until then where the player stands on the screen counted from where it was first seen; the furthest that place has been right, left, down and up is kept in pixels, and `look(moved, me, size)` returns the steps of the player's own larger side (4 to 32 pixels, fixed at the first sighting) newly passed, 4 a look at most with the rest not owed. `back()` puts the place back where the go began and keeps what was reached; `begin()` starts a go. `ScreenWatch` owns one and feeds it at every look (`_cover_ground`). A jolt is a look with no move believed and `JOLT` (2%) or more of the voting pixels still differing (the tracker's new `unexplained`). The watch calls `back()` when a jolt reaches `CUT` (a quarter), and when a jolt that follows a measurable look and finds the player further than its own size from where it was last seen falls within `BACK_LOOKS` (4) of a look that heard of a life lost. Every other jolt is a move it could not measure: nothing is counted for it, and `follows_camera` turns False while such looks are 20 or more and over a fifth of the last 200 looks in which the camera moved (kept from go to go); the steps are then counted and not paid, and `describe()` says so. `take_new_ground()` hands the steps over once. `EpisodeRunner._settle` now looks first, publishes `GroundCovered(frame, steps)` (in `services/observer.py`, next to `ButtonsHeld`), and only then takes the step's reward from the signals, so the pay is in the transition that earned it. `RewardService._on_ground_covered` adds the row `screen:new_ground` (`rewards/ground.py`: "Getting somewhere new", `Category.PROGRESSION`, `Trigger(EventKind.NEW_GROUND)`, suggested 1) the first time, unless dismissed, and scores one `NEW_GROUND` event a step through the same `_score` as every other row; the id is not named after an event kind, so `apply_suggestions` leaves it alone, and being Progression it counts as progress to the exploit detector. Limits: on the Toy Racer (64 by 48, up to 32 rows a look) the camera cannot be followed and the row pays next to nothing; no reward without memory access (the reward service is off there); a new room starts from the go's origin, so it under-pays; a respawn onto a screen with the same tiles that the tracker believes as a small move is not caught; on a screen that never scrolls a first jump and a first fall into a pit pay their steps (on one that scrolls they do not: the first version added the place on the screen to the camera's travel, and a fall then paid two or three steps at once, about what the life cost a second later).

**The camera's move between two looks (T-992).** `estimate_scroll(before, after, max_dx, max_dy, leave_out_before, leave_out_after)` still picks the shift under which the least of the new screen differs from the old (ties to the smaller move), now only among the pixels neither mask leaves out. Every shift is tried while that costs no more than 8 pixels of reach on a 256 by 240 screen did (`EXHAUSTIVE`: a small reach or a small screen); past that it ranks every `COARSE`-th (4th) shift on every 4th pixel, then tries every shift within 3 of the best `KEEP` (3), always including no move, and so can miss what only features thinner than 4 pixels tell. `ObjectTracker._camera_move` decides what may vote and whether to believe the answer. The `hide` box of this update and of the last (the player, which the camera holds still) is left out, and so are the rows in `_stuck` at `GLASS_AFTER` (2). If nothing else changed there is no move and no search; if all that changed fits in one small thing (half `max_size`, or an eighth of the screen if that is less, each way) there is no move either. The reach is `max_shift` or a quarter of the screen, whichever is less. A non-zero answer is believed only if it leaves at most `EXPLAINS` (half) of what differed still differing: the best of a bad lot, after a cut to an unlike place or a move past the reach, is no measure. After a believed move `_learn_glass` counts each row that holds something, did not change, and should have both ways (what the move brings is not there, what it held has not gone where the move takes it; where one of the two is off the screen the other decides); it clears rows that changed exactly as the move says, and takes one count off every other row, up to `GLASS_MOST` (4), so a mistake is let go. `_stuck` survives `reset()` and is dropped when the frame size changes. A thing lying wholly in glass rows gets `Track.glass`: it is matched without sliding by the scroll, its level is the screen (so `moves` is false), and glass rows are taken out of `_movers_in_scenery`. Things known to move are deliberately not left out of the vote: a wrong scroll makes the scenery's own edges look like movers, and excluding them kept the scroll wrong (measured: 35% right instead of 94%). `ScreenWatch` builds its tracker with `max_shift=LOOK_SHIFT` (32). Not handled: a cut to a place that looks alike (the same tiles: some shift then explains enough to be believed, once), a panel down the side of the screen, layers scrolling at different speeds, a strip that is one colour from end to end.

**What is around the player (T-989).** `observation/surroundings.py` is a pure reading of one screen: `read(frame, box, backdrop)` marks every pixel that is not the backdrop colour and answers five questions about the columns and rows next to the player's box, in steps of `STEP` (8) pixels up to `MOST` (6): the first column either side with nothing from the feet down to the bottom of the screen (`floor_right`, `floor_left`), the first column either side with anything in the top three quarters of the box's rows (`clear_right`, `clear_left`), and the first row with anything under the box (`under`: `ON_SOMETHING`, `NEAR_BELOW` within its own height, `FAR_BELOW`, `NOTHING_BELOW`). One pixel next to the box is left unread (`MARGIN`, the outline), and past the edge of the screen nothing is found. `ScreenWatch.look` calls it with the box of the look and the catalogue's backdrop whenever it sees itself (by colours or by track) and keeps the answer as `around`; `parts()` gives `around.parts()` first, then the mover parts; the T-988 fall rule's "nothing under it" is `around.under == NOTHING_BELOW`. `StateEncoder.refresh` takes `SCREEN_SEATS` (12) out of its most while a screen source is set, before the eight distance seats, so memory, distances and screen together never pass the feature map's width. Limits, stated in the module: a strip drawn along the bottom of the screen hides every gap, and decoration at the player's height reads as something in the way.

**Every life lost reaches the eyes, and falls (T-988).** `EpisodeRunner._settle` adds each step's `take_setbacks()` and `take_scores()` to `_unseen_lost` / `_unseen_scored` and hands the sums to `ScreenWatch.look` on the next step that has a screenshot (it used to pass only that step's own, dropping the steps between); `finish` hands a leftover life to `ScreenWatch.told(lost=)`, and `begin` zeroes both. `ScreenWatch` (with a colour signature) keeps the last sighting (`_last_box`), the one a look before it (`_before`) and whether the strip under the box down to the screen's bottom was all backdrop (`_open_below`, against `catalogue.background`). **A life count that bounces is not lives (T-864).** The lives rule in `understanding/variables.py` ("nearly only goes down, through a handful of values") is judged when a byte is first proposed, on what the tracker had seen by then; the user's 09:47 log showed one such guess paying "Losing a life" 116 times and "Gaining a life" 101 times in a 600-step go. `lives_bounce(stats)` says a byte that has gone up at least `BOUNCE_UPS` (4) times and down fewer than twice that often is not a life count (lives are lost one at a time and restored several at once on a restart, so a real one keeps downs at twice its ups or more). `DiscoveryService.doubt_bouncing()` runs inside every `review()`: each unconfirmed LIVES guess whose first byte bounces gets `bounces` evidence (weight 0) the first time and is rejected by the AI the next, the same two-step verdict as T-855, so the bogus reward is gone within two reviews. Confirmed or named guesses are never touched; health is left alone because it is meant to go both ways; a rejected guess stays as a record and a person can put it back.

**The memory view (T-862).** `ResearchDialog` adds a "Memory" group fed by what the app already holds: the observation service's latest snapshot and change tracker (bytes classed as `state`, their value now and change rate) and the knowledge (the guess at each address, its kind and confidence, its name). Rows are capped at `MAX_MEMORY_ROWS` with a filter by address, hex offset, kind or name, and refreshed with the rest of the live view. Naming goes through `DiscoveryService.name_value(region, offset, name)`, which confirms the AI's guess at that address under the name or proposes and confirms a named unknown there, saves, and announces the change so the rewards, steps and lists follow.

**A person's own rewards (T-860).** `EventKind.UP` / `DOWN` are emitted by the `EventDetector` only for values it was *asked* about (`ask(var_ids)`), which it tracks whatever their kind or confidence as long as they are not rejected; the cached watch list is keyed on the asked set too. `rewards/own.py` builds the row: id `mine:up:<id>` or `mine:down:<id>` (not an event kind, so `apply_suggestions` never touches it), name "<plain name> goes up|down", category Progression, `custom=True`. `DiscoveryService.ask_for` keeps the asked set and hands it to every detector it creates; `RewardService.add_own` / `remove_own` / `own` manage the rows and re-ask after every change and after a profile loads, so a reconnect brings the rows and the asking back together. One event per step the value moves is the reward unit; a per-unit amount is a possible later option.

**Rewards are offered for the best guess of each role (T-858).** `Knowledge.offered(at_least)` narrows `believed` to `OFFERED_PER_KIND` (1) seats per kind, `OFFERED_MANY` (3) for progress values and flags, ranked as `believed` ranks (confirmed first, then confidence, evidence, address) and returned in the knowledge's order. `plain_names(variables)` names each by a person's name or its role word (`ROLE_WORDS`: "Your score", "a life", "Health", "Progress", …), with "(2nd guess)" for later seats of one kind. `suggest_behaviours`, `merge_suggestions` and `GoalService.trigger_options` build from `offered` and those names, so the kid-facing lists are short and readable; the detector, long look, state and exploit watch still act on the 16 per kind of T-850, and the Discovery panel and the log keep the address.

**A go knows what paid it (T-857).** `RewardEarned` names the matched behaviours and the share each gave (its value), and `EpisodeSignals` adds those shares up per behaviour while listening, plus the reward or penalty of each goal step under `step:<id>`. `EpisodeResult.earned` is the tuple of `Earning(id, name, count, amount)`, biggest amount first, saved with the record (an old record loads with none). `describe_earned` words the top three and counts the rest, and the training service appends ", from …" to the go's log line, so a log from a real game shows which guesses the points really come from.

**Panels are docks (T-837).** `MainWindow` has no central widget: each `Panel` sits in a `QDockWidget` named `dock_<key>`, movable, floatable, closable, with nested and tabbed docks allowed, so the six can be rearranged, tabbed, floated, hidden and brought back from the toolbar's "Panels" menu (`toggleViewAction` per dock, then "Reset layout"). The default arrangement is DESIGN §10's all-visible layout (Game left, activity over rewards right, the other three along the bottom). `saveState`/`restoreState` keep the arrangement in `layout.bin` under the data folder, written on close; a missing or unusable file means the default, and tests build windows without one.

**Threads in the UI (T-817).** The GUI thread must never wait on an emulator. A real one answers over a socket in tens of milliseconds, and on the user's PC 30 screenshot round trips a second on the GUI thread made the window unusable. `ConnectBar` connects on a `QThreadPool`; `FramePump` captures each frame, `PlayClock` steps each frame and takes the memory snapshot after it (T-818), and `ControllerPad` sends each change of the held buttons (T-821, merging changes made while one is in flight), on their own one-thread pools and report back by signal; a tick that finds the previous one still running is skipped, so the real rate settles to what the link delivers. Services publish events from whichever thread they run on and `EventBridge` delivers them on the GUI thread; `ConnectionService` records a dropped link once even when two workers find it together. The training tick still runs on the GUI thread. A worker reports through `ui.worker.report`, which drops the report when the signal's owner was deleted while the request was out (the window closed during a five-second timeout, T-829).

**One request per frame (T-823).** While the game runs, `PlayClock` sends one bundled `step` per pulse carrying the pad's held buttons, the memory reads the observation service plans once per connection (`ObservationService.snapshot_reads`, `MemoryCapture.reads`) and, every `screenshot_every`-th pulse, a screenshot. The worker hands the bytes to `ObservationService.advance(frames, snapshot=…)`, so no second request is made, and the screenshot comes out of `PlayClock.frame_captured`; `GamePanel` shows it, feeds `observe_frame`, and keeps `FramePump` stopped while the clock runs. The pump serves a paused game, training, and emulators that cannot step. The pad still sends an `input` when the held set changes, so a press lands between pulses too. `GamePanel` steps at `CLOCK_FPS` and shows pictures at `DEFAULT_FPS`; `screenshot_every` is their ratio. A real emulator therefore answers one message per frame instead of three. The training episode's step does the same (T-824): `set_input` + `advance_frames` + the snapshot's read became one `step`. "Practise fast" (T-836) asks the emulator for its top speed (`FAST_SPEED`, 64x) while training runs in an AI mode and puts 1x back on pause, stop, a return to "Watch it play" or a mode change, since each step's frames otherwise run at the emulator's own throttle inside the round trip; meanwhile `GamePanel` drops the pump to `PRACTISE_FPS` pictures a second so the link belongs to the steps. The bridge script puts 100% back when the app leaves, if the app changed it.

## 5. BizHawk bridge protocol (ADR-005, T-110)

The app never links to BizHawk. A Lua script shipped with the app, `retro_ai_lab/emulator/bizhawk/retro_ai_lab.lua`, runs inside EmuHawk (Lua Console → Open script, or `EmuHawk.exe --lua=<path>`), listens on `127.0.0.1:43110` with LuaSocket (`require("socket")`; EmuHawk does not bundle it, so `socket.lua` next to the script loads the DLL from `luasocket/x64/` the way Archipelago's connector does; found on the user's PC in T-816), and the `bizhawk` adapter connects to it. The script is the server so that nothing has to be running before the child opens the emulator, and so a dropped app can reconnect.

**Sources checked (T-110):** the BizHawk Lua function reference (tasvideos.org/BizHawk/LuaFunctions) for every API named below, and Archipelago's `connector_bizhawk_generic.lua` as a worked example of LuaSocket + newline-delimited JSON on current EmuHawk. Nothing here was run on a real EmuHawk yet; T-117 does that on the user's Windows PC, and the "verify" column below says what it has to confirm.

### 5.1 Framing

One JSON object per line (`\n`), UTF-8, no newlines inside a message. The app sends requests, the script answers every request in order, one response per request:

```
→ {"id": 7, "cmd": "read", "reads": [{"domain": "RAM", "addr": 0, "len": 256}]}
← {"id": 7, "ok": true, "frame": 1234, "reads": ["AAEC…"]}
← {"id": 8, "ok": false, "error": "Unknown domain 'VRAM'."}
```

Binary data (memory bytes, screenshots) is base64. `frame` is `emu.framecount()` when the response was built. An unknown `cmd` or malformed line gets an `ok: false` response and the connection stays open; a closed socket ends the session and the script goes back to waiting for a connection.

### 5.2 Commands

| cmd | request fields | response fields | Lua API behind it | verify on real EmuHawk |
|---|---|---|---|---|
| `hello` | `script` (protocol version the app expects) | `script` (version), `bizhawk` (`client.getversion()`), `system` (`emu.getsystemid()`), `rom` (`gameinfo.getromname()`), `hash` (`gameinfo.getromhash()`), `domains` (`[{name,size}]` from `memory.getmemorydomainlist()` + `getmemorydomainsize`), `buttons` (keys of `joypad.get(1)`) | as listed | domain list format; button names per core |
| `read` | `reads: [{domain, addr, len}]` | `reads: [base64…]` | `memory.read_bytes_as_array(addr, len, domain)` | 1-indexed table order |
| `input` | `buttons: {name: bool}` | – | held set; `joypad.set(table, 1)` applied before every frame until changed | `joypad.set` must be repeated each frame |
| `step` | `frames` (≥1), optional `buttons`, `reads`, `screenshot`, `image_file` | `reads`, `image` (base64 PNG or null) or `image_file` (T-825) | sets input, `emu.frameadvance()` × frames, then reads and screenshot | frame advance while paused (see 5.3) |
| `screenshot` | optional `image_file` (a `.png` path the app chooses) | `image` (base64 of the file `client.screenshot(path)` wrote), or `image_file` when the app named one | `client.screenshot(path)` into the temp folder; file read back and deleted; the adapter decodes it with QtGui's `QImage` into an RGB `Frame` | format written (PNG expected), cost |
| `speed` | `percent` | – | `client.speedmode(percent)` | accepted range |
| `save` / `load` | `slot` (safe name) | `load` returns `loaded: bool` | `savestate.save(path)` / `savestate.load(path)` under the script's temp dir | path handling |
| `mode` | `free_run: bool` | – | see 5.3 | which mode works |
| `ping` | – | – | – | – |
| `bye` | – | – | closes the connection, unpauses | – |

Names the emulator uses (domains such as `System Bus`, buttons such as `P1 A`) are kept on the Lua side; the adapter maps them to the app's lowercase identifiers (`system_bus`, `a`) and back, so the app's types stay unchanged. The script offers only domains it can actually read: at `hello` it peeks the first byte of each listed domain and leaves out any whose read raises a .NET exception, saying so in the Lua console; a read that fails later names the domain, address and length in its error (T-832). A region the emulator refuses after the handshake (the user's NesHawk threw on `CPU registers` whole, though its first byte read fine) is dropped by the adapter when the refusal's message names it, and the capture plans again without it on the next step, so the game goes on with the regions that work (T-833). While connected the script turns EmuHawk's on-screen messages off (`client.displaymessages(false)`), since every screenshot would otherwise announce itself, and turns them back on when the app leaves. The adapter offers only live memory as regions (T-827): domains named for ROM, VROM, BIOS, a bus or a cartridge are listed by the bridge but not watched, since the observer reads every region whole every frame and a NES bus plus ROMs is 100 KB a frame against 2 KB of RAM, and reading a bus can touch hardware registers. Picture and sound memory (OAM, nametables, VRAM, palettes, CGRAM, APU RAM) is left out too (T-835): it is drawn from RAM every frame and the screen capture already shows it, and on the user's Super Mario Bros. its bouncing sprite bytes made 1646 watched values that read as lives lost and as resets, ending every go after a step or two.

### 5.3 Timing and the two run modes

The script's main loop serves whatever requests are waiting, then gives control back to the emulator, so each round trip costs at least one turn of the emulator loop (about 16 ms at 100% speed). That is why `step` bundles input, frames, reads and a screenshot into one request: a training step is one round trip.

* **Hold mode (default):** on `hello` the script pauses EmuHawk (`client.pause()`) and keeps itself responsive with `emu.yield()`. The game advances only on a `step`. This matches the fake adapter exactly: nothing happens between the app's steps. The first real run (T-831) showed that a paused EmuHawk never wakes a script waiting in `emu.frameadvance()`: in `MainForm.StepRunLoop_Core` a frame runs only when the emulator is unpaused or the user presses Frame Advance, and only a frame resumes frame-waiting scripts (`LuaConsole.UpdateAfter` → `ResumeScripts(true)`), while `emu.yield()` waiters are also resumed at the top of every turn (`ResumeScripts(false)`). So a `step` in hold mode calls `client.unpause()`, `emu.frameadvance()` once per frame, and `client.pause()` again from the resume after the last frame, before the next turn can run another. The pad needs the loop's order too: `joypad.set` fills an override store that `InputManager.RunControllerChain` latches into the controller at the top of a turn and `ButtonOverrideAdapter.FrameTick` clears before each frame, so the script sets the pad, gives one `emu.yield()` for the latch, then unpauses, and sets the pad again between frames. The `lupa` test host runs this loop order (latch, resume yielders, then a frame only when unpaused), which reproduces the real failure against the old script and passes with this one. A step of n frames costs n + 1 turns of the emulator loop, and the turn that serves a request is a paused one; since T-890 a request already waiting, or arriving within `SERVE_WAIT_S` (4 ms) of the last answer, is served in the same turn (`socket.select` on the app's socket, at most `SERVE_MOST` requests between yields), and each `step` answer carries `took.latch` and `took.frames`, the seconds spent waiting for the latch turn and running the frames.
* **Free-run mode (fallback, `mode free_run=true`):** the emulator is not paused, the loop calls `emu.frameadvance()` on every turn, and `step` waits for `frames` more frames to pass with the held input. The game then runs at the emulator's speed between steps, and the adapter's `advance_frames(n)` means "let n more frames go by".

The adapter reports `frame_advance` only in hold mode.

### 5.4 Throughput expectations

Memory reads are small (the app reads a few regions of up to a few KB per step; base64 adds a third). A screenshot is a PNG written to disk by the emulator. On the same PC (the default, host `127.0.0.1`/`localhost`) the adapter names the file (`image_file`, in the app's temp folder, one per adapter) and reads and deletes it itself, so no copy crosses the socket (T-825); for an emulator on another PC (`image_transfer="socket"`) the script reads the file back and base64s it in Lua, which costs 2 ms per 2 KB up to 70 ms per 200 KB of PNG (measured on Lua 5.4), plus a third more bytes on the wire. Memory reads still travel as base64; the app reads a few regions of up to a few KB per step on 8- and 16-bit consoles, but a 256 KB GBA region would cost the same 70 ms, so a file hand-over for large reads is the next step if the log shows `step` dominated by them. `Link` times every call and logs a per-command summary (count, average, slowest) every 5 s (T-819), so the user's log says what each command actually costs before any such change is made. `python -m retro_ai_lab.tools.profile_play` (T-830) plays for a few seconds in the real window, against the simulator or a running emulator, and prints the same per-command totals for the whole run beside the app's own costs: the frames the clock stepped against the frames it wanted, the snapshot bookkeeping per step on the worker, the screen diff and display per picture on the GUI thread, and the longest GUI stall. Against the simulator with NES-sized pictures the app keeps every frame at 60 fps with under 0.2 ms of its own work per step and per picture, so when a real emulator runs slowly in the app the round trip is where the time goes.

### 5.5 Testing without an emulator

The Lua script runs in CI inside `lupa` (Lua 5.4 in-process, matching EmuHawk's NLua), with the `emu`, `memory`, `joypad`, `client`, `savestate`, `gameinfo` and `socket` globals stubbed by a small Python harness that plays the Toy Racer. A pure-Python `BizHawkSimulator` speaks the same protocol over a real TCP socket for adapter and service tests. Tests under `tests/real_emulator/` are opt-in (`RETRO_AI_LAB_EMULATOR_PATH` and `RETRO_AI_LAB_TEST_ROM`, ADR-007) and run only on a machine with EmuHawk and a ROM; `docs/BIZHAWK.md` tells the user how. Between requests the app sends nothing, so the adapter's `check_link()` probes the socket (a readable socket with no bytes is a closed peer) for the UI's link watchdog.

## 6. Second emulator: VBA-M feasibility (ADR-010, T-808)

DESIGN.md §7 names "VisualBoyAdvance / VBA-M" beside BizHawk as a practical emulator to target. The spike checked what each candidate offers against the adapter contract (§3) and the bridge protocol (§5), from the projects' own sources and documentation. Nothing here was run; the first task on a chosen emulator does that, as T-117 did for BizHawk.

**Sources checked:** VBA-M's `README.md`, `CMakeLists.txt`, the `src/wx/lua/` sources on `master`, the `v2.2.3` tag, the SDL port's man page (`src/sdl/vbam.6`, the `--gdb` option); mGBA's scripting reference (mgba.io/docs/scripting.html) and the `mGBA-http` project as a worked example of a socket server in an mGBA script; the TASVideos VBA Lua function list (the old VBA-rr fork).

### 6.1 What each emulator offers

| need (adapter hook) | VBA-M v2.2.3 (released) | VBA-M `master` Lua engine (unreleased) | mGBA 0.10+ scripting |
|---|---|---|---|
| a way in | GDB remote stub, SDL port only, GBA only (`-G tcp[:PORT]`, port 55555) | Lua Console in the wx/Qt ports; `luaL_openlibs` only, **no LuaSocket** | Tools → Scripting; Lua with a `socket` API (`socket.bind`, `listen`, `accept`, `receive`, `send`, `received` callback) |
| game info | none | `emu.romname()`, `emu.getsystem()` | `getGameTitle()`, `getGameCode()`, `checksum(C.CHECKSUM.CRC32)`, `platform()` |
| memory_read | GDB `m addr,len` (any bus address) | `memory.readbyte/word/dword` only: **one call per byte**, no range read; bus addresses | `readRange(address, length)`; `emu.memory` domains with `base`, `size`, `name` (GBA: wram, iwram, vram, oam, io…; GB: wram, hram, vram…) |
| input | none | `joypad.set(port, table)` | `setKeys(mask)`, `addKey`, `clearKeys`; `keysRead` callback |
| frame_advance | none (instruction step only) | `emu.frameadvance()` (a coroutine yield; the host resumes the script once per frame), `emu.pause()`/`unpause()`, `registerbefore/after` | `runFrame()` ("run until the next frame"), `frame` callback; pausing from a script is **not documented** → verify |
| screen_capture | none | **none** (`gui.text/box/line/pixel` draw only) | `screenshot(filename)` |
| speed_control | none | `turbo` is a frontend global, not exposed | not documented → verify |
| save_states | none | `savestate.create/save/load` | `saveStateSlot/loadStateSlot`, `saveStateBuffer/loadStateBuffer` |
| systems | GBA (GB has no stub) | GB, GBC, GBA | GB, GBC, GBA |

### 6.2 Findings

1. **A VBA-M adapter is not feasible on the released VBA-M.** Every release up to v2.2.3 has no scripting and no remote-control interface. The GDB stub reads memory, but an adapter needs to press buttons, step frames and take save states, none of which the GDB protocol can do; it would give `memory_read` alone, which the training loop can't use.
2. **VBA-M's Lua engine on `master` gets most of the way, with three gaps.** It appeared after v2.2.3 and is not in any release or changelog yet. It can read memory, hold buttons and step frames (its `emu.frameadvance()` is exactly the hold-mode model of §5.3) and has save states. It cannot take a screenshot, reads memory one byte per call (a 256-byte region is 256 Lua calls per step, fine for the practice-sized reads but slow for scans), and has **no socket library**, so the bridge would need another transport: Lua's standard `io` library is open, so a file- or named-pipe-based exchange polled once per frame would work on Windows but at frame-rate latency per request and with the bundled `step` command doing all the work. Feasible, with `screen_capture` off, once a release ships it.
3. **mGBA matches the bridge protocol one call to one.** Its scripting API (0.10 and later) has sockets, a game title and checksum for the game id, range reads with named domains and sizes (the `hello` domain list), key setting, `runFrame()`, screenshots, and save states to slots or buffers. The `mGBA-http` project runs a socket server inside an mGBA script with these calls, so the route is known to work. The adapter would reuse the §5 protocol unchanged and the `BizHawkSimulator`/`lupa` test approach; the Lua script is a second file with the same commands. To verify on a real machine: whether `runFrame()` steps a paused emulator (hold mode) or whether the script must drive from the `frame` callback (free-run mode), and whether speed can be set from a script.
4. **Game Boy family games are already covered.** BizHawk runs GB, GBC and GBA through its Gambatte and mGBA cores, so the child can play these games with the existing adapter today. A second adapter adds a second emulator, not new games.

### 6.3 Decision (ADR-010, Accepted)

The second real adapter is mGBA, built as `emulator/mgba/` with a shipped `retro_ai_lab.lua` that speaks the §5 protocol (T-810, T-811); its real-machine checks (§6.4) run alongside BizHawk's (T-117) on the user's PC. VBA-M stays on the list: the objective in DESIGN.md §7 is kept, and the adapter is revisited when a VBA-M release ships the Lua engine, with the limitation (no screen capture, a slower transport) recorded then. Overturn by a VBA-M release that adds sockets or a screenshot call, or by the user preferring VBA-M for a reason the spike didn't see.

### 6.4 The mGBA bridge script (T-810)

`retro_ai_lab/emulator/mgba/retro_ai_lab.lua` speaks the §5 protocol unchanged, so the adapter, the simulator and the tests carry over. The differences come from mGBA's API, not the protocol:

| | BizHawk script | mGBA script |
|---|---|---|
| loop | the script owns the loop (`emu.frameadvance()` / `emu.yield()`) | event-driven: `callbacks:add("frame")`, `callbacks:add("keysRead")`, socket `received` events polled once a frame |
| run modes | hold (paused between requests) or free run | free run only: mGBA has no pause from a script, so `mode` is accepted and does nothing |
| `step` | runs the frames inside the handler and answers | arms a counter; the answer is sent from the `frame` callback once the frames have passed; another request meanwhile is refused ("A step is still running") |
| input | `joypad.set` of a table every frame | a key mask (`C.GBA_KEY`/`C.GB_KEY` bits) set with `emu:setKeys` on every `keysRead` |
| memory | named domains, `read_bytes_as_array` | `emu.memory` domains; `readRange(base + addr, len)` |
| game id | `gameinfo.getromname()`, `getromhash()` | `getGameTitle()` (or the game code), CRC32 from `checksum()` as 8 hex digits; `hello` also carries `code` and `emulator = "mGBA"` |
